# T12 OpenAI Responses adapter

The adapter uses the injected `model.HTTPClient` and the configured endpoint and API key. It defaults to the Responses profile and pins the configured model; it does not select a fallback model, discover credentials, or retry a paid `POST /responses` request. Requests use `store: false`, and provider-owned continuation items are carried as opaque JSON. Reasoning content is never converted to transcript text.

`Probe` and `ListModels` use bounded read-only GET requests. Probe reports the configured Responses contract as supported, while streaming, tool calling, and usage remain unknown until a separately recorded model capability profile verifies them. It never infers paid capabilities with a completion request.

Responses SSE text deltas are emitted as text events. Function call arguments are accumulated by call or item identity, including interleaved parallel calls. Tool events are buffered until response completion and emitted only after the provider marks the arguments complete, the JSON parses, the tool is registered, and the complete offline JSON Schema validation passes. Malformed, partial, or unknown calls return a typed provider error without a tool event. Completed responses carry authoritative usage only when both token fields are present and valid. Opaque continuation contains complete input/output history before the next turn’s new messages; interrupted responses do not emit usage.

The adapter classifies authentication, model, quota, cancellation, protocol, transport, and invalid-request failures without returning provider response bodies or credentials. Usage estimates use byte counts plus bounded structural overhead and remain unknown; they are planning estimates, not proof of a provider charge ceiling. The broker must reserve against the configured model/context and output limits, especially for opaque reasoning continuation. Every paid request requires an explicit positive output limit. Cancellation and protocol failure after dispatch retain uncertain usage.

Tests cover split and interleaved tool arguments, malformed and unknown tools, interruption with late usage, opaque continuation, pinned models, read-only probing, safe errors, and conservative estimates. They use HTTP fixtures only. No live API key or paid request was available, so live model capability, account quota, and provider-version qualification remain an integration gap.

The implementation follows the official [function calling](https://developers.openai.com/api/docs/guides/function-calling), [streaming Responses](https://developers.openai.com/api/docs/guides/streaming-responses), and [Responses create](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) documentation. The small Responses-only HTTP implementation preserves opaque output items and enforces the injected destination policy directly; it does not need the SDK’s broader resource surface or retry machinery.

Root review fixed stateless history replay order/shape, first-turn encrypted reasoning preservation, strict output/request limits, nested tool schemas, private redirect policy and uncertain dispatch errors. Package race tests and shared schema tests pass. Stateless replay follows the official [reasoning continuation contract](https://developers.openai.com/api/docs/guides/reasoning).

# Competition research

**Reviewed:** 20 September 2026. Sources are official product documentation or
the product's public repository. “No evidence” means the reviewed sources did
not document the capability; it does not prove that the capability is absent.
UX comments marked **[inferred]** are design judgments from the documented
workflow, not claims about an inaccessible product UI.

## Cross-competition findings

1. **[Inferred] Complete maintenance integration is the hypothesis.** OpenHands already combines a GUI, BYO models/agents, automation and enterprise controls; Devin and Cursor also have automation workspaces. Repo Steward, CodeScene, RepoWarden and Gitar provide other portfolio views. Reforge must prove an advantage in the complete Apache-2.0 team workflow across GitHub, GitLab and Gitea, dependency-bot cooperation and governed delivery. This review does not establish that the market is empty or that competitors cannot add these features.

2. **Provider breadth is uneven.** Renovate is the strongest reference for GitHub/GitLab/Gitea/Forgejo portability. Gitar and CodeRabbit cover several commercial providers. Cursor spans GitHub/GHES, GitLab/self-managed GitLab, Azure DevOps and Bitbucket, with provider-specific trigger differences and self-hosted workers. Jules and gh-aw remain documented around GitHub; Seer documents GitHub and GitLab. A product comparison must show provider and deployment scope per capability, not a single “integrations” badge.

3. **[Inferred] Policy is becoming the product boundary.** gh-aw uses read-only jobs plus safe outputs; Repo Steward stages actions and requires a maintainer decision; Renovate gates approval/automerge; Sentry exposes a stopping point; Aikido exposes severity gates; Gitar can manage lifecycle. The reusable unit is a policy decision with actor, scope, evidence, expiry and audit trail.

4. **[Inferred] AI choice matters but is not unique.** OpenHands, Patchwork, Repo Steward, Gitar and CodeScene document model/provider choice or BYO paths. Cursor documents Enterprise model controls and BYOK for Cursor usage, while its Automations docs do not establish BYOK for headless runs. Reforge should combine per-tenant/per-policy model routing and local endpoints with the complete three-forge maintenance workflow; BYO models or a GUI alone are insufficient positioning. Competitor subscription-bridge claims do not establish Reforge's own entitlement; see the provider-specific research.

5. **Maintenance tools need cooperation.** Renovate and Dependabot already group updates, schedule work, assign owners and can automerge after checks ([Renovate automerge](https://docs.renovatebot.com/key-concepts/automerge/), [Dependabot groups](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)). The app should ingest their PRs, deduplicate by dependency/CVE, preserve bot ownership, and optionally trigger an agent only when the bot's tests or policy indicate help is needed.

6. **[Inferred] Evidence beats agent claims.** Cursor attaches logs/screenshots/video; Repo Steward derives status from artifacts and GitHub facts; Gitar keeps a living summary; RepoWarden records test and bisection outcomes. Every run should expose inputs, model, permissions, commands, test results, diff, cost, policy decision and resulting PR/deployment.

7. **[Inferred] Security limits are UX requirements.** Documented risks include gh-aw permission/configuration review, Cursor internet and auto-run exposure, Repo Steward engine-dependent guardrails, and cloud code access across commercial tools. A coherent GUI should make trust boundary, network, secrets, write scope, branch target and approval state visible before dispatch.

## Concrete improvement candidates [inferred]

- A provider-neutral portfolio tree: tenant → organization/group → repository → branch/environment, with GitHub, GitLab and Gitea identities kept distinct but searchable together.
- A single “maintenance inbox” with dependency, security, CI, stale issue, drift and deployment items; deduplicate Renovate, Dependabot and native scanner signals while retaining source links.
- Per-repository policy cards: allowed change types, protected branches, required checks, merge/deploy authority, approval quorum, schedules, concurrency, network and secret scope.
- A run timeline that separates plan, approval, execution, verification, PR/MR, merge and deployment; every stage links to immutable evidence and supports retry or takeover.
- Agent profiles with BYO key/local endpoint, model, context budget, tool allowlist and cost cap; validate capabilities before a policy can select a profile.
- “Why this next?” ranking using severity, exploitability/reachability, dependency age, CI state, ownership, change frequency and deployment risk, with a human override recorded.
- A staged action preview that shows file diff, commands, tests, generated PR text, expected permissions and rollback path before any write.
- Cooperation modes for Renovate/Dependabot: observe, enrich PR, repair failed checks, group/supersede, approve, automerge, or hand off; never create a competing update by default.
- Portfolio health views inspired by CodeScene: repository freshness, failed maintenance rate, open-update age, policy coverage, ownership gaps and recurring failure clusters.
- Deployment-aware gates: associate a maintenance PR with the CI pipeline and environment, require promotion evidence, and stop at merge or deployment according to policy.
- Tenant-safe audit and retention controls: append-only action history, redacted prompts/logs, per-tenant encryption boundary, export, retention expiry and operator access trail.

These candidates are product opportunities inferred from the evidence above; they are not claims that any competitor lacks a GUI or that a documented feature cannot exist outside the reviewed sources.
